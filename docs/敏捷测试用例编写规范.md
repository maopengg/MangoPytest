# 敏捷测试用例编写规范

## 1. 概述

### 1.1 目的
本文档定义了敏捷开发模式下测试用例的编写规范，确保测试用例作为**长期资产**持续积累，同时执行记录作为**迭代活动**独立跟踪。

### 1.2 核心原则

```
用例是「资产」→ 跟功能/用户故事走（长期复用）
执行是「活动」→ 跟 Sprint/迭代走（每次新开一页）
```

### 1.3 适用范围
- 功能测试用例
- 接口测试用例
- UI 自动化测试用例
- 探索性测试记录

## 2. 用例字段规范

### 2.1 字段清单

| 序号 | 字段名 | 字段类型 | 必填 | 说明 |
|------|--------|----------|------|------|
| 1 | 用例编号 | 自动编号/文本 | ✅ | 建议格式：`TC-{模块缩写}-{0001}` |
| 2 | 用例标题 | 文本 | ✅ | 一句话清晰描述测试目的 |
| 3 | 优先级 | 单选 | ✅ | P0(🔴阻塞) / P1(🟠高) / P2(🟡中) / P3(🟢低) |
| 4 | 关联用户故事 | 关联字段 | ✅ | 关联「需求/故事表」，实现双向联动 |
| 5 | 迭代/Sprint | 单选/关联 | ✅ | 当前 Sprint 标识，如 Sprint 5 |
| 6 | 测试类型 | 多选 | ✅ | 功能 / 接口 / UI自动化 / 探索性 / 性能 / 兼容性 / 安全 |
| 7 | 前置条件 | 文本（多行） | — | 环境、数据、权限等准备工作 |
| 8 | 测试步骤 | 文本（多行） | ✅ | Markdown 列表格式，建议 5-8 步 |
| 9 | 预期结果 | 文本（多行） | ✅ | 与步骤一一对应，明确可验证 |
| 10 | 验收标准来源 | 文本（多行） | — | 直接粘贴用户故事的 Acceptance Criteria 原文 |
| 11 | 自动化状态 | 单选 | — | ❌未自动化 / 🔄计划自动化 / ✅已自动化 / ⛔无需自动化 |
| 12 | 自动化脚本链接 | 文本（URL） | — | 链接到 GitLab/GitHub 仓库具体文件路径 |
| 13 | 执行状态 | 单选 | ✅ | ⬜未执行 / ✅通过 / ❌失败 / 🚫阻塞 / ⏭️不适用 |
| 14 | 实际结果 | 文本（多行） | — | 失败时必填，记录实际表现 |
| 15 | 执行人 | 人员 | — | 飞书人员字段，支持 @ 通知 |
| 16 | 执行日期 | 日期 | — | 手动选择或自动记录 |
| 17 | 创建人 | 人员 | — | 自动填充当前用户 |
| 18 | 备注/探索性记录 | 文本（多行） | — | 探索性测试的观察、风险、建议 |

### 2.2 优先级定义

| 选项 | 颜色 | 含义 | 处理要求 |
|------|------|------|----------|
| P0 🔴 阻塞 | 红色 | 阻塞发布，必须当天解决 | 100%执行，阻塞需立即升级 |
| P1 🟠 高 | 橙色 | 核心功能，Sprint 内必须完成 | 100%执行，失败需当天跟进 |
| P2 🟡 中 | 黄色 | 重要功能，资源允许时执行 | 80%以上执行 |
| P3 🟢 低 | 绿色 | 边缘场景，可延后或抽样 | 抽样执行或延后 |

### 2.3 执行状态定义

| 选项 | 图标 | 说明 | 使用场景 |
|------|------|------|----------|
| 未执行 | ⬜ | 待安排测试 | 新用例或回归待执行 |
| 通过 | ✅ | 实际结果符合预期 | 测试通过 |
| 失败 | ❌ | 实际结果与预期不符 | 发现缺陷，需跟进 |
| 阻塞 | 🚫 | 因依赖问题无法执行 | 环境/数据/第三方依赖问题 |
| 不适用 | ⏭️ | 当前迭代该用例无需执行 | 功能未变更，无需回归 |

### 2.4 自动化状态定义

| 选项 | 图标 | 说明 |
|------|------|------|
| 未自动化 | ❌ | 当前为手工测试 |
| 计划自动化 | 🔄 | 已识别自动化价值，待排期 |
| 已自动化 | ✅ | 脚本已入库，可回归执行 |
| 无需自动化 | ⛔ | 探索性/一次性测试，不适合自动化 |

## 3. 用例编号规范

### 3.1 编号格式

```
TC-{模块缩写}-{4位序号}
```

### 3.2 模块缩写示例

各团队根据实际业务模块定义缩写，示例：

| 模块 | 缩写 | 示例 |
|------|------|------|
| 认证模块 | AUTH | TC-AUTH-0001 |
| 用户管理 | USER | TC-USER-0001 |
| 订单管理 | ORDER | TC-ORDER-0001 |
| 支付模块 | PAY | TC-PAY-0001 |
| 消息通知 | MSG | TC-MSG-0001 |
| 系统管理 | SYS | TC-SYS-0001 |

### 3.3 编号规则
- 用例编号全局唯一，不随 Sprint 变化
- 新增用例按模块顺序递增
- 删除用例后编号保留空缺，不补号

## 4. 用例标题规范

### 4.1 标题格式

```
[操作] + [对象] + [条件/结果]
```

### 4.2 示例

| ❌ 不好的标题 | ✅ 好的标题 |
|--------------|-------------|
| 测试登录 | 用户使用有效凭证登录成功 |
| 注册测试 | 新用户使用未注册手机号完成注册 |
| 订单 | 用户选择库存充足商品成功创建订单 |
| 审批 | 部门经理对报销申请执行通过审批 |

### 4.3 标题原则
- 一句话描述，不超过 30 字
- 明确操作主体（谁）
- 明确操作对象（什么）
- 明确预期结果（怎样）

---

## 5. 测试步骤规范

### 5.1 步骤格式

使用 Markdown 有序列表，一步一验证：

```markdown
1. 【动作】执行某操作
   → 【验证】预期结果描述

2. 【动作】执行下一步操作
   → 【验证】预期结果描述
```

### 5.2 步骤数量
- 建议 5-8 步
- 超过 10 步考虑拆分用例
- 少于 3 步考虑合并用例

### 5.3 步骤编写原则

| 原则 | 说明 | 示例 |
|------|------|------|
| 原子性 | 每步只做一件事 | ❌ "输入用户名密码并点击登录" → ✅ "1.输入用户名 2.输入密码 3.点击登录" |
| 可执行 | 步骤可直接操作 | ❌ "验证系统正常" → ✅ "页面跳转至首页，显示用户名" |
| 无歧义 | 描述精确具体 | ❌ "输入正确数据" → ✅ "输入手机号：13800138000" |
| 可验证 | 每步都有验证点 | 每个动作后紧跟预期结果 |

### 5.4 示例

```markdown
**测试步骤：**

1. 打开登录页面
   → 页面加载完成，显示用户名/密码输入框

2. 输入用户名：`testuser`
   → 用户名显示在输入框中

3. 输入密码：`password123`
   → 密码以掩码形式显示

4. 点击「登录」按钮
   → 页面跳转至首页
   → 右上角显示用户名
   → 本地存储写入 Token

5. 检查接口响应
   → 登录接口返回状态码 200
   → 响应体包含 token 字段
```

## 6. 预期结果规范

### 6.1 预期结果格式

与测试步骤一一对应，使用 `→` 符号连接：

```markdown
1. 【动作】xxx
   → 【验证】xxx
   → 【验证】xxx
```

### 6.2 预期结果原则

| 原则 | 说明 |
|------|------|
| 可观察 | 通过看/听/操作能直接判断 |
| 可度量 | 能用数据量化（响应时间 < 2s） |
| 无二义 | 结果明确，不会因人而异 |
| 完整性 | 覆盖 UI、数据、接口、日志各层面 |

### 6.3 验证维度

```markdown
→ UI 层面：页面显示、元素状态、提示信息
→ 数据层面：数据库记录、字段值、关联数据
→ 接口层面：状态码、响应体、响应头
→ 日志层面：系统日志、审计日志
```

### 7.2 示例

```markdown
**前置条件：**
1. 测试环境已就绪
2. 测试账号已注册且状态正常
3. 测试数据已准备完毕

```

## 8. 双表管理结构

### 8.1 表 A：测试用例库（跟功能走）

存储用例的静态信息，长期积累，不随 Sprint 变化。

| 用例编号 | 用例标题 | 关联用户故事 | 优先级 | 测试步骤 | 预期结果 | 自动化状态 |
|----------|----------|--------------|--------|----------|----------|------------|
| TC-USER-0001 | 有效手机号注册 | US-205 | P0 | ... | ... | ✅已自动化 |
| TC-USER-0002 | 重复注册拦截 | US-205 | P1 | ... | ... | ❌未自动化 |

### 8.2 表 B：执行记录（跟 Sprint 走）

存储每次执行的活动记录，每次迭代独立。

| 执行ID | 关联用例 | Sprint | 执行状态 | 实际结果 | 执行人 | 执行日期 |
|--------|----------|--------|----------|----------|--------|----------|
| EX-0001 | TC-USER-0001 | Sprint 5 | ✅通过 | — | 张三 | 2026-05-04 |
| EX-0002 | TC-USER-0002 | Sprint 5 | ❌失败 | 提示不准确 | 张三 | 2026-05-05 |
| EX-0003 | TC-USER-0001 | Sprint 7 | ✅通过 | — | 李四 | 2026-06-10 |

### 8.3 关联关系

```
测试用例库（表A）          执行记录（表B）
├── TC-001 <──────┐       ├── EX-001 → TC-001, Sprint 5
├── TC-002        │       ├── EX-002 → TC-002, Sprint 5
├── TC-003        │       ├── EX-003 → TC-001, Sprint 7
└── TC-004        │       └── EX-004 → TC-002, Sprint 7
                  │
                  └──── 一对多关联
```

## 9. 迭代中新增/修改用例的处理

### 9.1 场景处理矩阵

| 场景 | 处理方式 |
|------|----------|
| Sprint 首次开发功能 | 在「用例库」新建用例，关联用户故事，在「执行记录」添加 Sprint 执行行 |
| Sprint 功能增强 | 不改原用例，新建用例关联同一用户故事，原用例选择性回归 |
| Sprint 发现用例过时 | 在用例库修改用例，版本自动更新，执行记录关联最新版本 |
| Sprint 纯回归无新功能 | 在「执行记录」批量添加回归执行行，引用已有用例，不新建 |

### 9.2 用例版本管理

```
TC-USER-0001 (v1.0) → Sprint 5 创建
TC-USER-0001 (v1.1) → Sprint 7 修改步骤
TC-USER-0001 (v1.2) → Sprint 9 补充边界条件

执行记录关联具体版本：
EX-0001 → TC-USER-0001 v1.0
EX-0003 → TC-USER-0001 v1.1
```

## 10. 推荐视图配置

### 10.1 视图清单

| 视图名称 | 用途 | 配置 |
|----------|------|------|
| 🔴 当前迭代待测 | 每日站会看板 | 筛选：迭代=当前Sprint + 执行状态=未执行；分组：优先级 |
| ❌ 失败跟进 | 缺陷修复跟踪 | 筛选：执行状态=失败；排序：优先级+执行日期 |
| 🤖 自动化待办 | 技术债管理 | 筛选：自动化状态=计划自动化 |
| 📊 按优先级总览 | 冒烟测试清单 | 分组：优先级；排序：用例编号 |
| 👤 我的任务 | 个人工作台 | 筛选：执行人=当前用户 |
| 📈 用例执行历史 | 回归分析 | 按用例分组，看历次执行趋势 |

## 11. 自动化流程建议

### 11.1 自动化触发规则

| 触发条件 | 动作 |
|----------|------|
| 执行状态变更为 ❌失败 | 飞书消息通知：执行人 + 该用户故事的开发负责人 |
| Sprint 结束前 2 天，P0/P1 仍为 ⬜未执行 | 飞书群消息 @测试负责人 预警 |
| 关联用户故事状态变更为 已上线 | 自动将该用例执行状态重置为 ⬜待回归 |

### 11.2 自动化状态流转

```
❌未自动化 → 🔄计划自动化 → ✅已自动化
    ↓
⛔无需自动化（探索性/一次性测试）
```

## 13. 度量指标

### 13.1 用例质量指标

| 指标 | 计算方式 | 目标值 |
|------|----------|--------|
| 用例覆盖率 | 已编写用例的功能数 / 总功能数 | >= 95% |
| P0/P1 覆盖率 | P0+P1 用例数 / 总用例数 | >= 60% |
| 自动化率 | 已自动化用例数 / 总用例数 | >= 50% |
| 用例复用率 | 被多次执行的用例数 / 总用例数 | >= 70% |

### 13.2 执行质量指标

| 指标 | 计算方式 | 目标值 |
|------|----------|--------|
| P0 执行率 | P0 已执行数 / P0 总数 | 100% |
| P1 执行率 | P1 已执行数 / P1 总数 | >= 95% |
| 首次通过率 | 首次执行通过数 / 总执行数 | >= 85% |
| 缺陷逃逸率 | 线上缺陷数 / (线上缺陷+测试发现缺陷) | <= 5% |
