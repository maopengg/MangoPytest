**三条均已修复并通过验证。**

| 用例 | 涉及项目 | 2.0.5 + 1.50 | 2.1.0 + 1.62（修复前） | 定性 | 修复后 |
|---|---|---|---|---|---|

| `UI-EL-100` `w_upload_files` | simple_ui | 失败（超时） | 失败（语义拒识） | 既有问题，用例路径失效 | 通过 |

### 4.1 `UI-OP-049`：playwright 1.50 → 1.62 的 glob 语义变更

用例参数为 `url="**/"`，执行时页面 URL 为 `http://43.142.161.61:8003/#components`。
playwright 在 1.51+ 修改了 `**/` 的 glob 翻译规则：

```
glob = '**/'
URL                                     1.50    1.62
http://43.142.161.61:8003/              True    True
http://43.142.161.61:8003/#components   True    False   ← 回归点

1.50 正则: ^((?:[^/]*(?:/|$))*)$    # 可匹配任意 URL
1.62 正则: ^(.*/)$                  # 必须以 / 结尾
```

`page.wait_for_url()` 的实现在 1.62 为：当前 URL 匹配则立即返回，否则
`expect_navigation` 等待下一次导航；由于 `**/` 不再匹配 `#components`，
最终抛 `Timeout 5000ms exceeded`（日志：`waiting for navigation to "**/" until 'load'`）。

**修复位置（3 处，`**/` → `**`，已修改）：**

| 文件 | 位置 |
|---|---|
| `auto_tests/ui/pytest_ui/data/cases.json` | `operations` 中 `UI-OP-049` 的 `params.url` |
| `auto_tests/ui/bdd_ui/data/cases.json` | `operations` 中 `UI-OP-049` 的 `params.url` |
| `auto_tests/ui/simple_ui/data/MangoMock_UI全元素操作测试用例.xlsx` | `操作方法覆盖` 第 50 行「操作参数(JSON)」 |

> `**` 在 1.62 下翻译为 `(.*)`，等价于旧版 `**/` 的匹配效果。

### 4.2 `UI-EL-100` / `UI-OP-009`：simple_ui 的 Excel 使用了失效的文件路径

**真正的根因不在元素，而在用例参数。** 日志显示元素每次都定位成功：

```
[元素查找] 找到元素 -> ui-file-input, 数量: 1
[元素操作] 操作参数：{'locating': ..., 'file_path': '/…/tests/ui_excel_cases/data/upload.txt'}
```

simple_ui 的用例参数写的是 `${project_root}/tests/ui_excel_cases/data/upload.txt`，
该目录**从未存在过**（`git log -- tests/ui_excel_cases` 为空），是旧目录布局的残留；
真实文件在 `auto_tests/ui/simple_ui/data/upload.txt`。

直接验证 `locator.set_input_files()`：

| 传入路径 | 结果 |
|---|---|
| `/…/tests/ui_excel_cases/data/upload.txt`（Excel 中的值） | `FileNotFoundError: [Errno 2] No such file or directory` |
| `/…/auto_tests/ui/simple_ui/data/upload.txt`（真实文件） | 成功，已选文件数 = 1 |

bdd_ui / pytest_ui 不失败，正是因为它们的路径是
`${project_root}/auto_tests/ui/<项目>/data/upload.txt`，文件真实存在。

**修复位置（simple_ui 工作簿 3 处，值改为
`${project_root}/auto_tests/ui/simple_ui/data/upload.txt`，已修改）：**

| 工作表 | 行 | 位置 | 类型 |
|---|---|---|---|
| `操作方法覆盖` | 10 | 「操作参数(JSON)」列 | 实际执行（`UI-OP-009`） |
| `交互元素逐一操作` | 101 | 「参数(JSON)」列 | 实际执行（`UI-EL-100`） |
| `参数字典` | 15 | 「上传路径」行的「示例」列 | 文档示例，同样需改正以免继续教错路径 |

除上述 3 处外，全仓库 `bdd_ui` / `pytest_ui` 的 `cases.json` 与 `simple_ui` 其余
`${project_root}` 路径均指向真实存在的文件（已脚本全量核对）。

### 4.3 工作簿的修改方式（重要）

`MangoMock_UI全元素操作测试用例.xlsx` **不能用常规方式随意重写**，本次采用「解包 → 改
sheet XML → 重新打包」的方式，原因是：

- 待改字符串都是**内联在 sheet XML 的 `<x:v>` 节点**里（不在 `sharedStrings.xml`），
  用 `zipfile` 做逐条目替换即可，无编码或合并单元格风险。
- 该工作簿的 `[Content_Types].xml` 只用 `<Default Extension="xml">` 声明，
  而**没有** `/xl/workbook.xml` 的 `<Override>`，因此
  `office-skills/scripts/check_office.py` 的 `package` 检查会报
  `[Content_Types].xml does not declare xl/workbook.xml as .xlsx`。
  **这是原文件就有的问题，不是修改引入的**（已用修改前的备份复现同一报错），
  Excel 与 openpyxl 均可正常读写。
- 工作簿含 4 个 Table（`OperationCoverageTable`、`ElementInventoryTable`、
  `InteractiveElementCasesTable`、`ParameterDictionaryTable`），重写时需保留。

修改后已做逐条目校验：20 个 zip 条目顺序不变，仅
`xl/worksheets/sheet2.xml`、`sheet4.xml`、`sheet5.xml` 三个条目内容变化，
其余 17 个字节级一致。

#### 附：2.1.0 掩盖了真实异常（建议在内部包修复）

- 2.0.5 报错：`[300] 操作元素【ui-file-input】超时，请检查元素是否可见，或是否可以进行相应的操作`
- 2.1.0 报错：`[300] 智能定位失败：AI 找到了相似元素，但与元素描述不一致，请补充更明确的元素位置或周边文字`

2.1.0 的文案来自新增的 `mangoautomation/uidrives/_locator_failure.py`
（`reject_reasons` 含 `semantic mismatch` 分支），该逻辑在 2.0.5 中不存在。
此时 `AI_ELEMENT_HEALING_ENABLED = False` 且无 API Key，走的是**本地自愈**路径，
与 AI 服务无关，可稳定复现。

问题在于：重试策略把**操作级异常**（文件不存在）当成了**定位失败**——
元素已定位成功却仍重试约 10 秒，随后触发统一智能定位，
最终用自愈的拒识文案覆盖掉真正的 `FileNotFoundError`。
建议内部包对非定位类异常（参数非法、文件缺失等）直接抛出，不进入定位重试与自愈。
